## Classification Definitions

| Classification      | Meaning                                                                                      |
| ------------------- | -------------------------------------------------------------------------------------------- |
| `ALIGNED`           | Canonical meaning and the required material governance guarantees are present.               |
| `PARTIALLY_ALIGNED` | The core concept exists, but one or more required guarantees are missing.                    |
| `DIVERGENT`         | Current implementation contradicts a canonical distinction or permits an unsafe outcome.     |
| `MISSING`           | No current equivalent was identified.                                                        |
| `LEGACY`            | A superseded implementation is retained for compatibility, migration, or historical reasons. |
| `UNKNOWN`           | Available code or data evidence cannot establish current behaviour or data state.            |

Do not use `ALIGNED` merely because a similarly named table or field exists.

## Severity Definitions

| Severity        | Meaning                                                                                                                                |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `CRITICAL`      | Can expose unapproved, changed, clinically unsafe, or incorrectly governed content to learners or permit materially invalid decisions. |
| `HIGH`          | Can invalidate approval, publication, authority, versioning, or traceability guarantees.                                               |
| `MODERATE`      | Can produce drift, ambiguity, inconsistent workflows, or maintenance burden without immediate unsafe exposure.                         |
| `LOW`           | Creates limited governance incompleteness or local inconsistency.                                                                      |
| `INFORMATIONAL` | Recorded for completeness, future design, or terminology clarification.                                                                |

Alignment and severity are independent.

## Current Evidence Summary

Correct 0.1 findings retained:

- `CaseEditorialStatus` combines validation, review, approval, readiness, publication, and rejection concepts.
- `DiagnosisEducationStatus` combines drafting, generation, review, approval, publication, rejection, and archival concepts.
- `Case.currentRevisionId`, `CaseReview.revisionId`, `CaseValidationRun.revisionId`, differential mapping revision IDs, and differential link revision IDs are nullable.
- `CaseReviewContextSnapshot` and `CaseEditorialDecision` are stronger, newer case-governance constructs because they require exact `revisionId`.
- `DailyCase` schedules by mutable `caseId`, and gameplay reads mutable `Case` content.
- `User.role` and role helpers grant global technical access; `admin` inherits editor and senior-editor behavior.

Corrections applied in 0.2:

- `DiagnosisRegistry.status`, `active`, `isPlayable`, and `isGeneratable` are not divergent merely because they co-reside on `DiagnosisRegistry`. They are distinct stored operational/lifecycle fields. The missing guarantee is governance provenance and explainable readiness/decision context.
- `DiagnosisAlias` is `PARTIALLY_ALIGNED`, not `ALIGNED`, because alias governance provenance, rationale, ambiguity handling, and deactivation history are incomplete.
- `CaseReviewContextSnapshot` is a Review Packet Snapshot / Governance Source Context, not a generic Governance Record or Editorial Decision.
- `CaseReview` is split into review workflow and embedded legacy decision projection.
- `DiagnosisGraphCandidate` has aligned candidate-vs-fact separation, but candidate review, approval, merge, promotion, and decision provenance remain `PARTIALLY_ALIGNED`.
- Learning Goals may remain structured content within Editorial Brief unless stable identity, independent evolution, or cross-artifact linkage requires promotion.

Claims remaining `UNKNOWN`:

- Live production data completeness and historical row populations.
- Whether every deployed publication path consistently sets `Case.publishedAt`.
- Exact section numbers inside canonical PDFs/docs; canonical document identifiers are cited and section references are marked `UNKNOWN`.
- The full operational effect of any external manual database changes.
- Repository absence does not prove absence from external operational/manual governance processes.

## Compatibility Projection Principle

Existing fields such as `Case.editorialStatus`, `Case.approvedAt`, `Case.approvedByUserId`, `Case.publishedAt`, `DiagnosisEducation.editorialStatus`, `DiagnosisEducation.reviewedAt`, and `DiagnosisEducation.publishedAt` may remain temporarily as compatibility projections. Once canonical Governance Records and decisions become authoritative, these fields must be derived or synchronized only through governed command handlers and must not remain independent sources of truth.

## Interim Mutable-Publication Safeguard

Until learner exposure can reference an immutable published revision, Phase 1 recommends the following invariant for later enforcement design:

Published or scheduled cases must not be materially edited in place. A material edit should create a new `CaseRevision`, invalidate prior publication eligibility, clear or supersede approval/publication compatibility projections, and remove assignment eligibility unless a frozen publication snapshot or immutable published-revision reference is used.

## Follow-up Implementation Plan

### Phase 2: lifecycle and action catalogue

- Affected current models: `Case`, `DiagnosisEducation`, `DiagnosisRegistry`, `DiagnosisRegistryCandidate`, `DiagnosisTeachingRule`, `DiagnosisEditorialBrief`, `ReasoningPath`, graph/evidence relationship models, AI/clue draft status fields.
- Additive schema changes: none required initially; add metadata/action catalogue in code.
- Expected migrations: none.
- Compatibility risks: low while read-only; risk rises if services enforce before shadow-mode testing.
- Compatibility projection principle: current statuses remain projections only until governed command handlers own transitions.
- Tests required before enforcement: every current enum/string status maps to explicit canonical concepts without implying unrelated concepts.

### Phase 3: typed Governance Records and source contexts

- Affected current models: `CaseReviewContextSnapshot`, `CaseEditorialDecision`, `CaseReviewEvent`, `AiDraftRevisionAudit`, `DiagnosisRegistryCandidate`, graph/evidence review fields.
- Additive schema changes: governance record architecture with artifact type, artifact identity, exact revision identity for every versioned artifact, governance question, actor, authority exercised, findings, rationale, outcome, effect, prior state, resulting state, remaining obligations, timestamp, and source Review/Assessment references.
- Expected migrations: additive create-table migrations plus indexes.
- Compatibility risks: duplicate decision sources unless old fields are treated as compatibility projections.
- Tests required before enforcement: every material decision records exact revision when versioned; review-context snapshot remains source context, not decision.

### Phase 4: readiness and blocker engine

- Affected current models/services: `CaseValidationRun`, `ReasoningDraftValidationRun`, `ReasoningPath.readinessScore`, `DiagnosisEditorialOnboardingService`, `CaseEligibilityPolicyService`, workspace quality services.
- Additive schema changes: operation-specific readiness result records and blocker/warning payloads if persisted.
- Expected migrations: additive readiness tables if persisted.
- Compatibility risks: disagreement between existing statuses/projections and computed readiness.
- Tests required before enforcement: readiness explains operation, blockers, warnings, stale conditions, and never substitutes for approval.

### Phase 5: scoped authority and permission matrix

- Affected current models/services: `User.role`, `UserOrganization`, `roles.ts`, `editorial.guard.ts`, `admin.guard.ts`, permission decorators.
- Additive schema changes: authority assignments/scopes by organization, artifact family, specialty, workflow, or publication capability.
- Expected migrations: additive authority tables.
- Compatibility risks: admin workflows may rely on current inherited permissions.
- Tests required before enforcement: admin technical access is distinct from editorial/publication authority.

### Phase 6: controlled application and version-specific approval enforcement

- Affected current models: `Case`, `CaseRevision`, `CaseReview`, `CaseValidationRun`, `CaseClueRevisionDraft`, `AiDraftRevisionAudit`, `DiagnosisEducation`, `DiagnosisEducationRevision`.
- Additive schema changes: controlled application records, revision-specific approval enforcement, material-change rule catalogue, backfill tracking.
- Expected migrations: additive tables first; later backfill migrations for legacy records.
- Compatibility projection principle: `Case.approvedAt`, `Case.approvedByUserId`, `Case.editorialStatus`, and education review fields become derived/synchronized projections.
- Compatibility risks: legacy rows with nullable revisions require `UNKNOWN` or `LEGACY` classification.
- Tests required before enforcement: accepted AI draft does not apply change; controlled application creates/references revision; approval targets exact revision; material edits invalidate dependent decisions.

### Phase 7: publication decision and immutable learner exposure

- Affected current models/services: `Case`, `CaseRevision`, `DailyCase`, `DiagnosisEducation`, `DiagnosisEducationRevision`, `DailyCasesService`, `CaseAssignmentService`, gameplay read models.
- Additive schema changes: publication decision records, published artifact version records, immutable learner exposure references, optional release events.
- Expected migrations: additive publication tables; later backfill `DailyCase` published revision references.
- Interim safeguard: scheduled/published cases cannot be materially edited in place unless learner reads use a frozen publication snapshot.
- Compatibility projection principle: `Case.publishedAt`, `CaseEditorialStatus.PUBLISHED`, and `DiagnosisEducation.publishedAt` become derived/synchronized projections from publication decisions.
- Tests required before enforcement: approval is not publication; scheduling is not publication; learner exposure points to immutable published revision/snapshot.

### Phase 8: migration, shadow mode, maintenance, and enforcement

- Affected current models: all mapped editorial artifacts and governance records.
- Additive schema changes: compatibility/backfill tracking, conformance status, enforcement flags, maintenance ownership/revalidation obligations.
