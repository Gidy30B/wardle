# WEOS Permission Map

Runtime roles and canonical authority are not proven equivalent by the repository.
Use this map to decide whether a runtime user can call an application route; do
not use it as proof of institutional or canonical WEOS authority.

## Interpretation Warning

Runtime access is not canonical authority.

The repository proves that users with certain runtime roles may call protected
routes. It does not prove that those users hold canonical publication,
governance-board, clinical-approval, educational-approval or institutional
authority.

The helper name `canPublishEditorial` is a runtime compatibility name. It means
that the role is `senior_editor` or `admin`. It must not be interpreted as proof
of canonical `AUTHORISE_PUBLICATION` authority.

## Layer A: Runtime Role Lattice

| Runtime role    | `canAccessEditorial` | `canPublishEditorial` | `canAccessAdminOps` | Effective runtime scope                     | Canonical authority |
| --------------- | -------------------: | --------------------: | ------------------: | ------------------------------------------- | ------------------- |
| `user`          |                   No |                    No |                  No | Ordinary learner/user routes                | None implied        |
| `editor`        |                  Yes |                    No |                  No | Editor-level routes                         | Not proven          |
| `senior_editor` |                  Yes |                   Yes |                  No | Editor and senior-editor routes             | Not proven          |
| `admin`         |                  Yes |                   Yes |                 Yes | Editor, senior-editor and admin-only routes | Not proven          |

Runtime role inclusion:

```text
admin
  -> satisfies senior-editor helpers
  -> satisfies editor helpers

senior_editor
  -> satisfies editor helpers

editor
  -> does not satisfy senior or admin helpers
```

This is a runtime helper lattice, not an institutional authority hierarchy.

## Authorization Patterns

### Editor-Level Route Pattern

```text
Controller guard:
AdminGuard

Method decorator:
EditorialAccess

Metadata:
editor

Minimum runtime role:
editor

Also allowed:
senior_editor, admin
```

`EditorialAccess` also applies `EditorialGuard`, while `AdminGuard` reads the
same metadata at the controller layer.

### Senior-Level Route Pattern

```text
Controller guard:
AdminGuard

Method decorator:
SeniorEditorialAccess

Metadata:
senior

Minimum runtime role:
senior_editor

Also allowed:
admin
```

### Admin-Only Route Pattern

```text
Controller guard:
AdminGuard

Method decorator:
None

Editorial metadata:
None

Minimum runtime role:
admin
```

Stable classification:

```text
ADMIN_ONLY
```

Meaning:

```text
The route is protected by AdminGuard and has no editor or senior editorial
metadata. Non-admin editorial roles are rejected.
```

### Payload-Restricted Editor Route

```text
Route permission:
editor

Additional controller assertion:
AdminController.assertDraftLevelStatus

Effect:
Editors may use the route for draft-level writes but cannot submit configured
senior-only status literals.

Limitation:
This is controller payload validation, not generic service-layer or database
authorization.
```

## High-Risk Permission Mismatches

1. Runtime editors can accept AI drafts.
2. Runtime editors can approve clue revision drafts.
3. Runtime editors can apply approved clue revision drafts.
4. Senior runtime access to readiness does not prove publication authorization.
5. Education publish is coupled with review semantics.
6. Graph candidate approval may couple approval with fact promotion.
7. Evidence relationship activation may have node activation side effects.
8. Admin bypasses editor and senior role distinctions at the runtime guard level.
9. Frontend `canPublishEditorial` is not backend or canonical authority.
10. Local QA uses configured ordinary roles and does not create a special authority class.
11. Payload-level status assertions are limited controls, not universal service enforcement.
12. Most services enforce state transitions rather than actor authority.

## Agent Permission Decision Rule

Before invoking a runtime action, an agent must determine:

1. The exact route and request decision.
2. The controller guard.
3. The method decorator and editorial metadata.
4. The minimum runtime role.
5. Any payload-level status restriction.
6. Any service-level authorization.
7. Whether frontend controls are merely presentational.
8. Whether canonical authority is proven.

Runtime access answers only whether the current application permits the call. It
does not answer whether the action is canonically authorized under WEOS.
